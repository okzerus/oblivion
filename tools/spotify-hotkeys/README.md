# Spotify mouse hotkeys

Управляет десктопным клиентом Spotify на Windows через кнопки мыши,
без использования системных медиа-клавиш и OSD.

## Управление

| Действие                                   | Комбинация            |
|---------------------------------------------|------------------------|
| Play / Pause                                 | mouse5                 |
| Следующий трек                               | Ctrl + mouse5          |
| Предыдущий трек                              | Ctrl + mouse4          |
| Развернуть Spotify поверх всего / свернуть в трей, если уже в фокусе | Ctrl + Shift + mouse5 |

mouse4/mouse5 — боковые кнопки мыши (x1/x2). Любой клик без нужного
модификатора (например, просто mouse4, или Ctrl+mouse4 вместе с Shift)
скрипт не трогает — он проходит как обычно (например, «назад»/«вперёд» в
браузере).

Лайка текущего трека нет: единственный способ узнать, что сейчас играет,
не спрашивая само окно Spotify — это Spotify Web API, а его player-эндпоинты
(`currently-playing` и т.п.) требуют Premium. Ломать функцию под часть
пользователей смысла не было — вырезано полностью.

## Как это работает

- **При запуске скрипта** (то есть при входе в систему, если настроен
  автозапуск): если процесс `Spotify.exe` не найден, скрипт сразу его
  запускает — не нужно ждать, пока сам вспомнишь открыть Spotify, чтобы
  заработали хоткеи. Запускается сразу в трей, без мелькания окна на
  экране: используется тот же трюк, что и в известном C++/`ShellExecute`
  решении для этой задачи — при создании процесса передаётся `SW_HIDE`
  (через `STARTUPINFO`/`wShowWindow`, ровно то же самое, что
  `ShellExecute(..., SW_HIDE)`, только штатными средствами
  `subprocess.Popen`, без компиляции отдельной программы). Чем это лучше
  флага `--minimized`: `--minimized` — недокументированный флаг самого
  Spotify, и на практике он просто сворачивает окно в панель задач, а не
  в трей. `SW_HIDE` же передаётся на уровне создания процесса Windows —
  окно не показывается вообще с первого кадра, до того, как Spotify успеет
  что-либо с ним сделать. Трей-иконка при этом появляется как обычно, она
  создаётся независимо от видимости главного окна. На случай, если будущая
  версия Spotify перестанет учитывать `SW_HIDE`, скрипт подстрахован:
  если окно всё же покажется, оно будет сразу свёрнуто в трей через тот же
  `WM_CLOSE`, что и обычное сворачивание. Мышиный хук при этом
  устанавливается сразу, не дожидаясь запуска Spotify, — хоткеи на
  воспроизведение просто ничего не будут делать первые несколько секунд,
  пока он не откроется.

  Если у вас в настройках Spotify включено "Open Spotify automatically
  after you log into the computer" — выключите её. Иначе Spotify может
  запуститься сам, в обход этого скрипта, обычным (видимым) образом ещё до
  того, как скрипт успеет что-то сделать.
- **Команды воспроизведения** (play/pause, next, previous) отправляются
  напрямую в окно Spotify через `WM_APPCOMMAND` (`SendMessageTimeout`), а не
  через системные медиаклавиши. Поэтому не появляется оверлей Windows и не
  затрагиваются другие проигрыватели (например, вкладка с YouTube).
- **Перехват кнопок мыши** сделан через низкоуровневый хук `WH_MOUSE_LL`
  (raw WinAPI через `ctypes`, без сторонних библиотек). Состояние Ctrl/Shift
  проверяется через `GetAsyncKeyState` в момент клика — отдельный хук
  клавиатуры не ставится, поэтому обычный ввод с клавиатуры никак не
  затрагивается. Хук умеет сам себя переустанавливать (сразу при
  разблокировке экрана и вдобавок каждые 20 секунд на всякий случай) — см.
  "Хоткеи ломались после блокировки/разблокировки экрана" ниже.
- **Разворачивание поверх полноэкранной игры**: скрипт использует стандартный
  обход ограничения `SetForegroundWindow` (временное подключение через
  `AttachThreadInput` + кратковременный `HWND_TOPMOST`). Для окна в
  оконном/безрамочном полноэкранном режиме Spotify просто появится поверх.
  Для игр с эксклюзивным полноэкранным режимом DirectX сама Windows свернёт
  игру при переключении фокуса — это стандартное поведение системы, как при
  Alt+Tab, и обойти его без сворачивания игры невозможно в принципе.
- **Открытие из полностью скрытого в трей состояния** (когда иконки нет даже
  на панели задач) идёт не через прямой `ShowWindow`, а через повторный
  запуск `Spotify.exe` — см. "Исправленные баги" ниже.
- **"Закрытие" Spotify, когда он уже в фокусе**: скрипт посылает окну Spotify
  `WM_CLOSE` — то же самое сообщение, которое получает окно при нажатии на
  крестик. Чтобы это сворачивало в трей, а не закрывало программу полностью,
  в самом Spotify должна быть включена настройка **"Свернуть в трей при
  закрытии"** (Settings → Show desktop icon / Minimize to tray on close).
- **Запуск Spotify**: если окно не найдено, скрипт сначала проверяет, не
  запущен ли процесс `Spotify.exe` вообще (через `CreateToolhelp32Snapshot`,
  без сторонних библиотек) — если да, но окно ещё не создано (Spotify только
  стартует), повторный запуск не выполняется, чтобы не открыть вторую копию.
  Если процесса нет — запускается `%APPDATA%\Spotify\Spotify.exe` (это и
  есть путь вида `C:\Users\<Вы>\AppData\Roaming\Spotify\Spotify.exe` —
  определяется автоматически через переменную окружения), с резервным
  вариантом через `spotify:` URI, если этот файл не найден.

## Исправленные баги

### Хоткеи переставали работать, а иногда зависал весь рабочий стол

Самый серьёзный из найденных багов: при частых быстрых нажатиях (например,
play/pause подряд несколько раз за секунду) хоткеи через некоторое время
переставали реагировать — а в одном случае это привело к тому, что **вся
мышь на рабочем столе** перестала на что-либо нажимать (ни значки, ни
панель задач), пока это не "чинилось" блокировкой/разблокировкой экрана
(Win+L и обратно).

Причина — временная версия скрипта писала в лог-файл диагностические
сообщения прямо из тела `WH_MOUSE_LL`-хука. Это хук особого рода: через
него последовательно проходит **весь мышиный ввод во всей системе**, для
всех программ разом, а не только клики, которые мы обрабатываем — Windows
буквально ждёт, пока коллбэк вернёт управление, прежде чем доставить
событие дальше. Запись в файл — это синхронный диск I/O с непредсказуемой
задержкой (антивирус, загрузка диска, блокировки), и под частыми кликами
подряд она способна была задержать сам коллбэк дольше, чем Windows готова
ждать — отсюда и зависание уже не только хоткеев, а всего рабочего стола.

Исправление — из тела хука убрано вообще любое логирование и любой другой
потенциально блокирующий вызов; коллбэк теперь только читает состояние
модификаторов и кладёт действие в очередь (`queue.Queue.put`, не
блокируется). Всё логирование, включая ошибки внутри самого хука, теперь
происходит в отдельном потоке-воркере, который не участвует в системном
input-pipeline и может как угодно долго писать на диск, не влияя на отклик
мыши.

### Хоткеи умирали через ~10 секунд именно при автозапуске (но не при ручном запуске)

Отдельный от предыдущего баг, обнаруженный именно на автозапуске через
планировщик: скрипт запускался, Spotify показывался в трее, хоткеи
работали — и ровно через несколько секунд после перехода на рабочий стол
переставали отвечать, без единой ошибки в логе. При этом тот же самый
`.exe`, запущенный вручную (после того как рабочий стол уже полностью
загружен), работал сколько угодно долго без единого сбоя — то есть дело
было не в коде, а именно в том, **в каком состоянии находился рабочий стол
в момент установки хука**.

Причина — таймер триггера **«При запуске» (At startup)** отсчитывается от
включения компьютера, а не от входа в систему. Если задача при этом ждёт
входа пользователя ("Run only when user is logged on"), она стартует, как
только вход происходит — но если это совпадает с моментом, когда explorer
и рабочий стол ещё не до конца доинициализировались, хук может
установиться на **временный объект рабочего стола**, который Windows
подменяет на финальный несколькими секундами позже. Хук при этом не
удаляется и не выдаёт ошибку — он просто перестаёт видеть реальный ввод,
потому что физически привязан уже не к тому рабочему столу.

Исправление в двух местах:
- Триггер планировщика — использовать **«При входе в систему»** вместо
  «При запуске» (см. раздел про автозапуск ниже): его задержка, если
  нужна, отсчитывается от самого входа, а не от загрузки, что гораздо
  предсказуемее.
- Скрипт теперь сам подстраховывается независимо от способа запуска: перед
  установкой хука он ждёт (до 60 секунд) появления `Shell_TrayWnd` — окна
  панели задач, надёжного признака того, что explorer и рабочий стол
  полностью готовы. Запуск Spotify при этом не откладывается — музыка
  по-прежнему начинается сразу, ждёт только сама установка хука.

Этого оказалось недостаточно — см. следующий пункт, там окончательное
решение.

### Хоткеи ломались после блокировки/разблокировки экрана — окончательный фикс

Выяснилось, что предыдущие два бага были лишь частными случаями одной более
общей проблемы. Подтвердилось это так: (1) быстрая блокировка и почти
сразу разблокировка экрана ломала уже нормально работавшие хоткеи (медленная
блокировка на несколько секунд — не ломала); (2) хоткеи ломались через
пару нажатий даже при **ручном** запуске скрипта сразу после разблокировки
экрана, то есть безо всякого планировщика, автозапуска или PyInstaller —
именно то, что должно было быть железно исключено предыдущими фиксами.

Причина — блокировка экрана переключает рабочий стол на отдельный
защищённый объект Windows (secure desktop, тот же механизм, что и у UAC),
а затем переключает обратно при разблокировке. Низкоуровневый хук
(`WH_MOUSE_LL`) привязан к конкретному объекту рабочего стола в момент
установки — переключение туда-обратно способно молча "осиротить" уже
работавший хук (та же механика, что и в предыдущем баге с логином, только
не разовая при старте, а потенциально при **любой** блокировке экрана в
течение дня) и точно так же способно сделать нездоровым **свежеустановленный**
хук, если он ставится в узкое окно времени сразу после переключения обратно,
пока состояние ещё не устаканилось до конца. Ни один из предыдущих
точечных фиксов (ожидание `Shell_TrayWnd`, разные триггеры планировщика)
этого не покрывал, потому что оба относились только к самому первому
запуску скрипта, а не к его работе в течение дня.

Вместо того чтобы гадать точные условия поломки (они оказались
невоспроизводимы стабильно даже в рамках одной сессии), скрипт теперь
чинит сам себя двумя независимыми, дополняющими друг друга способами:

- **Мгновенная реакция на разблокировку.** Скрипт создаёт невидимое окно
  (`HWND_MESSAGE`) и подписывается на уведомления сессии через
  `WTSRegisterSessionNotification`. Как только приходит `WM_WTSSESSION_CHANGE`
  с `WTS_SESSION_UNLOCK` (или `WTS_SESSION_LOGON`), хук снимается
  (`UnhookWindowsHookEx`) и ставится заново (`SetWindowsHookExW`) — заново
  привязываясь к актуальному на этот момент рабочему столу.
- **Периодическая переустановка по таймеру, независимо ни от чего.**
  Отдельный поток каждые 20 секунд просит основной поток (через
  `PostThreadMessageW` — переустановка хука обязана происходить именно в
  потоке, который его ставил) точно так же снять и поставить хук заново —
  без всякой привязки к тому, ЧТО именно могло его сломать. Это работает
  даже если по каким-то причинам не удалось создать окно для
  WTS-уведомлений, и на случай ещё не обнаруженного триггера поломки:
  худший случай — до 20 секунд неотвечающих хоткеев, а не полная поломка
  до следующего ручного перезапуска.

Сама переустановка занимает микросекунды и незаметна при обычном
использовании. Вместе эти два механизма должны сделать по-настоящему
залипший навсегда хук практически невозможным сценарием.

### Замороженное окно после разворачивания из трея

Если Spotify был полностью скрыт в трей (без иконки на панели задач), и его
разворачивали напрямую через `ShowWindow` (в том числе через цикл
minimize → restore — первая попытка исправить это не сработала), окно
показывалось "живым", но фактически замороженным — ничего не анимировалось,
кнопки не нажимались. При обычном разворачивании из панели задач (когда
иконка там оставалась) такого не было.

Оказалось, что при повторном запуске `Spotify.exe`, пока он уже работает
(даже скрытый в трей), сам Spotify корректно активирует и показывает своё
существующее окно вместо запуска второй копии — это и есть его встроенный
механизм разворачивания, и он не ломает рендер, в отличие от прямых вызовов
`ShowWindow` снаружи. Теперь скрипт использует именно это: вместо
`ShowWindow` для скрытого окна он просто запускает `Spotify.exe` ещё раз и
ждёт, пока окно станет видимым, — дальше уже применяется обычное
принудительное разворачивание поверх всего (см. выше).

### Третье нажатие ничего не делало

После разворачивания из трея и последующего закрытия (второе нажатие) окно
Spotify пряталось, но Windows иногда продолжал считать его "в фокусе"
(`GetForegroundWindow` возвращал его хендл, хотя окно уже не видно) — из-за
этого третье нажатие снова уходило в ветку "закрыть", посылая `WM_CLOSE`
уже скрытому окну, то есть ничего не менялось. Исправлено проверкой
видимости окна (`IsWindowVisible`) перед тем, как считать его
сфокусированным: скрытое окно теперь всегда обрабатывается как "нужно
показать", независимо от того, что говорит `GetForegroundWindow`.

### Иногда не получалось закрыть окно сразу после открытия

Обратная ситуация: сразу после открытия (особенно из полностью скрытого
состояния, когда открытие идёт через повторный запуск `Spotify.exe`)
следующее нажатие иногда снова открывало/разворачивало окно вместо того,
чтобы его закрыть. Судя по всему, `GetForegroundWindow` не всегда успевает
отразить переключение фокуса сразу же после того, как скрипт сам его
только что выполнил — сказывается гонка между собственной активацией
Spotify (при повторном запуске) и принудительным `SetForegroundWindow` из
скрипта.

Исправлено тем, что и открытие, и закрытие теперь не считаются
завершёнными сразу после соответствующего вызова, а дожидаются (до 0.5–1
секунды), пока `GetForegroundWindow`/`IsWindowVisible` не подтвердят
реальный результат, прежде чем скрипт продолжит обрабатывать следующее
нажатие. Если и полсекунды не хватило — довключается уже имевшийся трюк с
синтетическим Alt.

## Требования

- Windows 10/11.
- Python 3.8+ — используется только стандартная библиотека (`ctypes`),
  никаких `pip install` не требуется.

## Тихий запуск (без консоли)

`python.exe` всегда открывает консольное окно — это свойство самого
интерпретатора, не скрипта. Чтобы консоли не было вообще, есть два пути:

1. **`pythonw.exe` вместо `python.exe`** — тот же Python, но без консоли
   в принципе, ни при каком способе запуска. Указывается как "Программа" в
   планировщике (см. ниже).
2. **`run_hidden.vbs`** (лежит рядом со скриптом) — двойной клик или ссылка
   на него в планировщике запускает `hotkeys.py` через `pythonw`
   в полностью скрытом окне (`shell.Run ..., 0, False`), без единого
   мелькания консоли. Проще, если не хочется искать точный путь до
   `pythonw.exe` — скрипт сам берёт его из PATH (стандартно после установки
   Python с галочкой "Add to PATH"). Если PATH не настроен, впишите
   в `run_hidden.vbs` полный путь к `pythonw.exe` вместо `"pythonw"`.

Двойной клик по самому `.py` файлу или запуск через `python hotkeys.py`
в открытом терминале — единственные способы, которые покажут консоль, это
ожидаемо и не баг.

## Запуск при старте Windows

Важный технический момент: низкоуровневый хук мыши работает только в рамках
интерактивной сессии рабочего стола, которой **не существует до входа в
систему**. Поэтому буквально "до логина" такой скрипт функционировать не
может — это ограничение самой Windows, а не скрипта. Ближайший к этому
моменту, с которого хук может реально начать работать, — это **вход
пользователя в систему**, и именно на него стоит настраивать автозапуск.

Планировщик заданий (Task Scheduler) с триггером **"При входе в систему"**
предпочтительнее папки автозагрузки: элементы автозагрузки Windows
специально придерживает на несколько секунд после входа (staggered startup),
а задания планировщика запускаются сразу, независимо от того, успели ли
стартовать другие программы — то есть именно то поведение, которое нужно.

### Две отдельные задачи (рекомендуется)

Лучше не пытаться совместить «запустить Spotify как можно раньше» и «сам
хоткей-скрипт» в одной задаче на «При запуске» — помимо всего сказанного
выше про интерактивную сессию, если собирать скрипт в `.exe`
(см. "Альтернатива без Python" ниже), именно на «При запуске», когда
система и так занята десятком других стартующих программ, риск поймать
задержанное срабатывание антивируса на свежераспакованном exe — самый
высокий (см. troubleshooting-пункт про падение памяти ниже). Поэтому
задачи стоит развести:

**Задача 1 — запуск Spotify**, один из двух вариантов:
- `launch_spotify.vbs` (лежит рядом со скриптом) — максимально примитивный
  VBScript без Python и без самораспаковки, просто запускает `Spotify.exe`
  скрыто (`shell.Run ..., 0`). Ему почти нечем зацепить эвристику
  антивируса, так что ему безопаснее всех стартовать в самый загруженный
  момент загрузки системы.
- `tray.py` (тоже рядом со скриптом) — та же идея, но на
  Python, с тем же `SW_HIDE`-трюком и подстраховкой через `WM_CLOSE`, что
  и в `hotkeys.py` (см. "Как это работает" выше), если хочется
  держать логику в одном месте/языке, а не дублировать её в VBScript.
  **Важно**: запускать именно как `pythonw tray.py`, а
  **не** компилировать в `--onefile` — самораспаковка `--onefile` в самый
  загруженный момент загрузки системы это ровно то, из-за чего вообще
  понадобилась Задача 1 отдельно (см. troubleshooting-пункт про падение
  памяти ниже); `--onedir` тоже нежелателен здесь без необходимости — это
  просто лишний процесс интерпретатора, который не нужен для файла на
  10 строк смысла.
- Триггер: **«При запуске»** (At system startup), задержка по вкусу.
- Общие: «Выполнять только для вошедших пользователей» (тогда Spotify
  окажется в интерактивной сессии и получит доступ к трею — см. "Session 0
  isolation" ниже, если перепутать этот пункт).
- Действие: Программа — `launch_spotify.vbs` **или** `pythonw.exe` с
  аргументом `"C:\путь\к\tray.py"`.

**Задача 2 — хоткей-скрипт** (собственно `hotkeys`):
- Триггер: **«При входе в систему»** (At log on) — «Пользователь: [ваша
  учётная запись]», без задержки. **Не** «При запуске» — даже с «только
  для вошедших пользователей» это не то же самое и ведёт себя менее
  предсказуемо, см. предупреждения ниже.
- Общие: «Выполнять только для вошедших пользователей». Повышенные
  привилегии не нужны — Spotify всегда работает без администраторских
  прав, поэтому и скрипт не стоит запускать от админа.
- Действие: «Запуск программы» — один из вариантов:
  - Программа: `run_hidden.vbs` (самый простой, ничего искать не надо), или
  - Программа: путь к `pythonw.exe` — например
    `C:\Users\<User>\AppData\Local\Programs\Python\Python3xx\pythonw.exe`,
    Аргументы: `"C:\путь\к\hotkeys.py"`.
  - Рабочая папка (для второго варианта): папка со скриптом.
- Параметры: включить «Перезапускать через 1 минуту, до 3 раз» на случай
  сбоя — единственное, что нужно для устойчивости к падениям, всё
  остальное скрипт обрабатывает сам (переживает отсутствие запущенного
  Spotify, ошибки при отправке сообщений и т.д.). Сам скрипт всё ещё
  проверяет при старте, не запущен ли уже Spotify, и запускает его сам,
  если задача 1 почему-то не сработала — это подстраховка, а не замена
  первой задаче.

Если пре-логин звук не нужен — можно обойтись только Задачей 2, тогда
Spotify запустится сразу после входа тем же способом (см. `launch_spotify`
в самом скрипте).

### Если настроено как "At startup" + "Run whether user is logged on or not"

Симптомы именно этой неправильной конфигурации: Spotify всё-таки
запускается и даже играет музыку (в том числе слышно на экране блокировки),
но после входа в систему — (1) хоткеи вообще не реагируют и (2) значок
Spotify полностью отсутствует в трее, хотя процесс в диспетчере задач есть.

Причина — изоляция сессий Windows (Session 0 isolation, начиная с Vista):
задача с «независимо от входа пользователя» выполняется в отдельной,
неинтерактивной сессии, у которой нет доступа к рабочему столу
залогиненного пользователя. Аудио оттуда достаёт (звуковая подсистема этим
ограничением не связана), а вот низкоуровневый хук мыши — не видит реальных
кликов пользователя (он в другой сессии), и у Spotify по той же причине
физически нет способа создать окно/значок в трее на **вашем** рабочем
столе. Это не баг скрипта, а осознанное ограничение безопасности Windows
(защита от так называемых shatter-атак) — обойти его нельзя, только
запускать иначе.

Исправление — вернуться к сочетанию, описанному выше: триггер **«При входе
в систему»** + **«Выполнять только для вошедших пользователей»** (снять
галку «независимо от того, выполнен ли вход пользователем в систему»).
Расплата небольшая: музыка перестанет играть на экране блокировки и
запустится сразу после входа в систему — что для домашнего использования
обычно даже лучше (Spotify не будет слышно, пока вы ещё не вошли).

Уже запущенный "осиротевший" процесс Spotify из старой сессии сам не
пропадёт и не переедет в новую при следующем входе — его нужно закрыть
вручную (Диспетчер задач → Завершить задачу; если не даёт — с правами
администратора, либо проще один раз перезагрузить компьютер) перед тем,
как проверять исправленную настройку.

### .exe-версия умирает через ~10 секунд именно при автозапуске

Симптомы: собранный `.exe` запущенный планировщиком на «При запуске» (даже
с «только для вошедших пользователей») отрабатывает несколько секунд
идеально, потом хоткеи перестают отвечать — при этом в диспетчере задач
процесс остаётся в списке, но его потребление памяти резко падает (были
замечены цифры вроде 11 МБ → 0.8 МБ). Если после этого завершить задачу и
запустить тот же `.exe` вручную — он с этого момента работает без единого
сбоя сколько угодно.

Падение памяти — это симптом архитектуры `--onefile` в PyInstaller: сам
`.exe` — это загрузчик, который при каждом запуске распаковывает Python и
все зависимости во временную папку и запускает уже их как отдельный
дочерний процесс; именно дочерний процесс несёт всё состояние скрипта
(поток-воркер, хук и т.д.) и весит те самые ~11 МБ. Когда он падает —
загрузчик остаётся висеть сам по себе, вот и остаётся тот призрачный
~0.8 МБ процесс. То, что падает именно дочерний процесс, а не сам код
скрипта — верный признак, что дело не в логике Python, а во внешнем
вмешательстве в файл/процесс, и самый вероятный кандидат — антивирус,
с задержкой сканирующий свежераспакованные во временную папку файлы
(частая история именно для PyInstaller onefile-сборок), причём именно
во время загрузки системы, когда она и так занята под завязку — что
объясняет, почему повторный ручной запуск позже (когда всё уже
устоялось, а файл уже один раз проверен и признан безопасным) больше
не вызывает проблем.

Что помогает:
- Разнести автозапуск на две задачи, как описано выше — тогда в
  максимально загруженный момент («При запуске») стартует только
  примитивный `launch_spotify.vbs`, а не тяжёлый скомпилированный `.exe`;
  сам хоткей-`.exe` запускается позже, отдельной задачей на «При входе в
  систему», в уже гораздо менее нагруженный момент.
- Собирать `--onedir` вместо `--onefile` (см. ниже) — это вообще убирает
  самораспаковку во временную папку при каждом запуске, а вместе с ней и
  саму причину для срабатывания антивируса на "новый" файл.
- Проверить Windows Security → Защита от вирусов и угроз → Журнал защиты
  на предмет блокировки/карантина `.exe` в момент проблемы, и при
  подтверждении — добавить исключение для папки со скриптом.

### Альтернатива без Python

Скрипт можно собрать в отдельный `.exe`, чтобы вообще не зависеть от
наличия Python в системе (и от `run_hidden.vbs` — `--noconsole` даёт то же
самое "тихо" на уровне exe):

```
pip install pyinstaller
pyinstaller --onedir --noconsole hotkeys.py
```

**`--onedir`, а не `--onefile`** — судя по симптомам в предыдущем разделе,
именно самораспаковка `--onefile` во временную папку при каждом запуске
провоцирует задержанные срабатывания антивируса на файлах в этой
автозапускаемой задаче. `--onedir` запускает exe напрямую, без
распаковки — вместо одного файла получится папка (`dist\hotkeys\`)
с exe и зависимостями рядом, её и указывать в планировщике как «Программа»
(сам `hotkeys.exe` внутри). Если по каким-то причинам всё же нужен
именно `--onefile` — то как минимум разносите задачи по разделу выше.

## Логи

Скрипт пишет лог в `%LOCALAPPDATA%\SpotifyHotkeys\hotkeys.log`
(с ротацией) — туда стоит смотреть, если что-то не срабатывает: не найдено
окно Spotify, хук не установился и т.д.

## Известные ограничения

- Один запущенный экземпляр за раз (проверяется через именованный mutex) —
  повторный запуск просто тихо завершится.
- Если у Spotify когда-нибудь изменится класс главного окна
  (`SpotifyMainWindow`), скрипт подстрахован резервным поиском окна по имени
  процесса (`Spotify.exe`), но это стоит иметь в виду при странном поведении
  после обновления клиента.
- Скрипт не тестировался вживую в этой среде (linux-контейнер без Windows) —
  проверьте все комбинации (mouse5, ctrl+mouse4/5, ctrl+shift+mouse5,
  включая разворачивание поверх полноэкранной игры, восстановление из
  полностью скрытого в трей состояния и блокировку/разблокировку экрана)
  на реальной машине перед тем, как полагаться на автозапуск.
